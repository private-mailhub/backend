# Mail worker Lambda: prepare first, cut over separately

**A merge only tests.** `deploy-worker.yml` is main-only, manual and disabled by default. The default preview uses a role that cannot execute a change set. For an actual isolated or production publish, review the preview, choose **publish**, enable protected environment variable `WORKER_PUBLISH_ENABLED=true`, and authorize the narrowly scoped `WORKER_PUBLISH_ROLE_ARN`. The job checks STS account identity after assuming that role. Neither release mode can change the queue mapping. The operator-owned `mapping.yaml` stack is separate; create it **disabled** with the existing queue ARN and the WorkerAlias output, using a distinct cutover role. Its batch size is 1, max concurrency 2. The publish/CFN roles must have no permission to update this stack or Lambda mappings. Enable only by separate approval after verified PM2 drain, with both `EnableConsumption=true` and `ConsumerOwner=lambda-exclusive`. Set protected `WORKER_CONSUMER_OWNER=lambda-exclusive` only after the same evidence; release preflight rejects foreign or transitioning mappings and requires this attestation for a live alias. Remove the attestation before returning ownership to PM2. No example secret, key, account, or production message is needed for CI.

## Verify locally

Use `.nvmrc` (24.14.1), npm, `zip`, and Ruby (standard-library YAML for the cross-stack capacity check). From the repository root:

```sh
npm ci --engine-strict
npm run worker:test
ruby scripts/worker/check-capacity.rb
node --test scripts/worker/*.test.cjs
npm run worker:package
sam validate --lint --region us-east-1 --template-file infra/worker/template.yaml
```

The package uses `tsc` (including Nest/TypeORM decorator metadata) and the committed root lock, without a new bundler or dev packages. `infra/worker/build/worker.zip` contains only the worker's compiled source graph and locked runtime packages; imported handler is smoke-tested without any environment settings. Worker CI has no AWS credential step, OIDC grant, deploy command, or live fixture. Runtime: managed `nodejs24.x`; local and CI build pin Node 24.14.1, not Lambda's patch version. Secrets Manager, Lambda and CodeDeploy SDK v3 clients come from the managed Node runtime. Test resolution by invoking the **published version's** read-only probe in the isolated account after runtime patch changes.

## Prerequisites and trust

If a suitable DLQ does not already exist, see the [optional queue-owner DLQ handoff](optional-dlq/README.md). It is separate from both the worker release and the mapping.

* Use separate protected GitHub environments `worker-isolated` and `worker-production`. Require reviewers, main-only deployments, no self-approval. Configure repository `WORKER_CHANGESETS_ENABLED=true` only after review. Configure environment-specific variables listed in `deploy-worker.yml`. Keep the known production account ID independently protected. Trust OIDC audience `sts.amazonaws.com` and only this repository's exact environment subject. Change-set role: read preflight/stack state, write only the artifact prefix, create/describe (not execute) change sets, and pass only the named CloudFormation role. The execution role cannot be assumed directly by GitHub. Restrict its IAM/PassRole scope and resource prefixes, including SAM's generated CodeDeploy service role, in the target account.
* Supply **existing** same-account, same-region standard source queue, corresponding DLQ, private mail bucket/prefix, artifact bucket, two Secrets Manager ARNs, worker SG, and private subnets. The stack does not own or replace SES rules/identities, S3 notifications, S3 buckets, SQS policies/queues or DLQs. It cannot update their settings. Confirm event envelope shape; non-S3/foreign sources fail closed. Use `get-queue-attributes` to confirm redrive target, **3 to 5 receives**, visibility **at least 270 seconds** (6 × 45-second function timeout), DLQ retention longer than source, and delivery policy permitting that source. Verify any CMK key policies. Correct pre-existing settings only under separate owner approval, never using the rollout script.
* Do **not** create a NAT gateway. Use existing private, non-public database endpoint (or already approved RDS Proxy) and SG-to-SG SQL ingress, existing S3/Secrets Manager routes and DNS, and an already-approved HTTPS egress path to the Mailgun regional API for production. The Lambda service polls SQS; the process does not make queue calls. If Mailgun or any dependency is unreachable from the private subnet, stop. An isolated capture does not need Mailgun egress. Cloud costs include Lambda, SQS polling, Secrets Manager, existing egress/endpoints, Logs, alarms and artifact storage. Budget and alarms owner must approve before execution.
* Supply a dedicated least-privileged DB principal for mail tables only, not the RDS master or a migration user. The database secret is a JSON object with `host` (certificate hostname), `dbname`, `username`, `password`, optional `port`. App secret: `APP_NAME`, `APP_DOMAIN`, `ENCRYPTION_KEY`, optional `LEGACY_ENCRYPTION_KEYS`; production additionally needs `MAILGUN_API_KEY` and `MAILGUN_BASE_URL` (US or EU HTTPS API root). Do not copy API JWT, Redis, OAuth, static AWS keys or other API configuration. Nothing retrieves secret values in Actions or puts them in CloudFormation/Lambda environment variables. Encryption format must match the existing worker; do not rotate application keys as a rollout step. Cold starts fetch current secrets. After rotation recycle execution environments through a reviewed version update; leave old DB/application credentials valid for the staged handoff. TLS verifies both the CA chain (`/var/runtime/ca-cert.pem`) and exact hostname using mysql2's `verifyIdentity`. No SSL verification bypass.
* Apply the additive `mail_deliveries` migration separately on the correct DB, with backup and old-worker compatibility reviewed. Runtime sync and migrations are disabled. The function reserves **3 concurrent invocations** across all versions: the one live SQS mapping is capped at **2 deliveries**, leaving one slot for the sequential pre/post-traffic candidate probes. Avoid simultaneous manual invocations during a release. With a two-connection pool per execution environment, budget for up to **6 DB connections from active worker environments** (2 deliveries + 1 probe), plus idle pools on old/new warm environments and other DB clients. Six is not a database-wide connection limit. Verify regional Lambda quota and RDS headroom before rollout; do not increase queue throughput to use the spare slot.

## Isolated fixture and production handoff

1. Use a **different AWS account** with only synthetic MIME in an isolated bucket, dedicated source queue/DLQ, fixture DB, synthetic relay entries and isolated encryption key. Never route production SES or production S3 notifications into the test. No production provider key is required: the stage uses an in-memory MIME capture transport; only its `capture:<digest>` receipt is persisted. Require its execution role to have no SES-send permission and firewall egress to external providers. Create/inspect the separate change set; confirm no replacements, and separately create the mapping stack with `EnableConsumption=false`. An authorized operator can execute it independently.
2. On the first deployment SAM has no prior published version to shift from. Directly invoke `CandidateVersion` with `{"probe":"mail-worker.readiness.v1"}` and verify `ready:true` and the exact numeric version (read-only secrets + TLS + ledger columns), then check alias/alarms. Later updates use 10%/5-minute CodeDeploy, with **both** hooks probing exactly the candidate even if no real mail arrives. A hook failure or one failed record, Lambda error, throttle, DLQ visible message, or queue age ≥10 minutes can roll back the alias. Check CodeDeploy status and alias/version after rollback; idle metrics alone are not proof of success. Configure operational alarm notifications in the monitoring system before cutover; the template connects alarms to CodeDeploy, not to a pager.
3. In the isolated account only, enable the fixture mapping, seed `fixture-relay@example.invalid` as an active fixture relay and inject `infra/worker/fixtures/forward.eml` and publish its S3 notification twice. Expect one `sent` ledger row with capture receipt, no external route, and eventual source-queue drain. Include a valid sibling plus malformed body, verify the valid sibling is not resent and poison reaches DLQ after the configured receives. Verify inactive alias -> `skipped`, expected hash, test key decoding, forwarded/reply MIME and DLQ alarm. Disable test mapping and confirm `Disabled` before cleanup. Never replay a production message for this drill.
4. Before production: approve scope/cost, confirm backup, private routes, RDS capacity, secret rotation ownership, pre-existing queue redrive, and current PM2/consumer inventory. Ensure the deployed PM2 fallback already uses the same ledger/keys and drains on stop. Prepare and review production change set and candidate probe with **mapping disabled**. Freeze releases; stop/drain the PM2 worker only (keep API online), confirm no scheduled restart or additional poller and no in-flight owner, then enable exactly the production alias-bound mapping by a separately authorized operation. The workflow never does this. Track backlog, ledger states, provider receipts, Lambda concurrency/errors, failed records and DLQ continuously. Without verified PM2 drain and staged evidence, do not cut over.
5. Rollback: disable the Lambda mapping, wait for `Disabled`, running invocations and the source visibility interval; inspect ledger/queue/provider reconciliation before resuming only the compatible PM2 worker. Do not run both consumers or purge/recreate source/DLQ/S3. Handle mail/PII only in the restricted operational system, never paste payloads/secret values into logs or tickets.

**Redrive is not a repair for ambiguous sends.** Unknown/malformed envelopes remain unacknowledged and go to the existing DLQ. Pre-send transient failures may retry. A committed `sent`/`skipped` object is not resent on envelope replay. `sending`/`unknown` may already have reached the provider; quarantine and reconcile with deterministic message ID, provider receipt and ledger. Do not reset/release that fence or bulk-redrive until an operator has conclusive provider evidence. A provider timeout is not proof of non-delivery. Retain ambiguous records for manual investigation if delivery cannot be proven. No exactly-once claim.
