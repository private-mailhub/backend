# Optional dead-letter target: queue-owner handoff

Use [this standalone template](template.yaml) only if the source owner confirms no suitable DLQ exists. It creates one service-named Standard queue in `us-east-1`. Its `byQueue` allow policy permits one existing source to designate it as a DLQ; it does **not** attach the source, grant IAM access or move messages. Neither the worker release nor the mapping deploys it. CI only validates it:

```sh
ruby infra/worker/optional-dlq/test_template.rb
```

1. **Verify the source without reading messages.** Match the queue owner's independent inventory to the deployed PM2 queue configuration. A supplied name or constructed ARN is not proof. With authorized metadata access (`GetQueueAttributes`), inspect the ARN, FIFO status, retention, current redrive target, visibility and encryption. Require Standard, the same stack account and `us-east-1`, and source retention **strictly below 1,209,600 seconds**. Stop on a mismatch or unknown owner; do not shorten retention to pass.
2. **Preview only.** Obtain explicit queue-owner authorization to create and review a change set for a **new, distinct stack**. Supply the verified friendly `ExistingSourceQueueName`, not an ARN or URL. Expect one **Add** of `AWS::SQS::Queue`: no modifications, imports, deletions, replacements or IAM capabilities. Check the single-source ARN, encryption, retention and both retain policies.
3. **Create the target only.** Require **separate explicit execution authorization** for that exact change set. After execution, verify the generated ARN against the `DeadLetterQueueArn` output and recheck the attributes and single-source allow policy. Record the ARN and owner in restricted inventory. The source must still be unchanged.
4. **Attach separately.** Only with a **new, reviewed source-owner change**, update the existing source in place: `RedrivePolicy` targets that exact ARN, `maxReceiveCount` is **3 to 5**, and `VisibilityTimeout` is **at least 270 seconds** (6 × the 45-second Lambda timeout). Recheck the effective attributes; reject source replacement or displacement of an existing DLQ. Keep Lambda consumption disabled.

**PM2 is affected before cutover.** Once the source is attached, repeatedly unacknowledged mail can leave PM2's retries for the DLQ even with Lambda disabled. Review the live build, backlog and existing retries **before** approving the source change. The repository's PM2 poller requests 60-second per-receive visibility; the higher queue default does not extend those receipts. Before a separately approved [cutover](../README.md#isolated-fixture-and-production-handoff), verify exactly the expected source-to-alias mapping is **Disabled**. Stop/drain only the ledger-compatible PM2 worker; require `Queue polling drained`, no restart, other poller or in-flight attempt before enabling that mapping. A forced stop is not drain evidence.

**Retention, privacy and operations.** Standard SQS preserves the original enqueue time on dead-lettering; 14 days is not 14 fresh days in the DLQ. `DeletionPolicy: Retain` and `UpdateReplacePolicy: Retain` preserve the queue, not messages past expiry. Track the retained queue even if the stack is removed. Do not purge, replay/redrive, delete retained data or recreate either queue. No alarms or IAM/queue access policies are provisioned. Before attaching, assign an on-call owner, verify paging on the first visible DLQ message, monitor source backlog/oldest age and in-flight counts, and budget SQS requests and monitoring.

The target uses SQS-managed server-side encryption (SSE-SQS), not a customer-managed KMS key. Moving messages to a DLQ preserves their original encryption state; verify the source's encryption and any key-access requirements independently. Treat envelopes, object keys and mail metadata as private: restrict access, require TLS and do not put payloads in logs or tickets. For `sending`/`unknown`, **quarantine, do not resend**. Reconcile the fenced ledger, deterministic message ID and provider receipts in the restricted operational system; a timeout or missing receipt is not proof of non-delivery. No message operations, source edits, mappings, migrations or deployments are part of validating this template.
