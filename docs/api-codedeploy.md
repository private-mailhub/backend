# EC2 API CodeDeploy contract

This revision deploys only the Nest HTTP API. It never installs an Nginx site, changes frontend files, operates on `mailhub-worker`, starts all ecosystem entries, saves the global PM2 dump, runs migrations, or builds on the host. Use a separate API-only, in-place EC2 deployment group. Before enabling it, disable competing old deploys, including any prior CodeDeploy revision with a destructive `ApplicationStop` hook. No instance traffic or load-balancer lifecycle hooks are needed.

## Revision and host prerequisites

At ZIP root: `appspec.yml`, executable `deploy/codedeploy/api.sh` and all its sibling `.cjs` files, `deploy/release.sh`, `revision.txt` (one 40-hex commit), `backend.tar.gz`, and `backend.tar.gz.sha256` (one standard `sha256sum backend.tar.gz` line). The tar contains `dist/` including `dist/main.js`, `package.json`, `package-lock.json`, `.nvmrc`, and `deploy/ecosystem.config.cjs`. No secrets, dependencies or worker-specific replacement commands are bundled. The checksum detects archive damage; CodeDeploy/S3 version pinning and the restricted release role supply provenance.

Use a disposable Linux clone to verify *these exact prerequisites* first. The hook deliberately refuses to bootstrap production:

- Install Bash, GNU tar, util-linux `flock`/`runuser`, `ss`, `getent`, systemd, Nginx and root-administered `/usr/bin/node` (Node 18+). The **service user** must separately resolve Node 24.14.1, npm and its existing PM2 binary. Check the daemon PID, `PM2_HOME/rpc.sock` ownership and real API name/CWD/PID/listener. Do not start a second PM2 daemon. Reserve both 8080/8081 for API use, allow loopback probes, and deny public connections to either port.
- Provision `/var/www/mailhub-backend/releases` writable only by the service account/administrator, and `/var/www/mailhub-backend/shared/.env` as a regular, service-readable file outside releases. Supply sufficient disk for a clean second installation, memory for the old and candidate APIs together, and the approved npm registry/cache. The service account needs read access to the runtime config, not root powers.
- Pre-create the same `/var/lock/mailhub-deploy.lock` used by other deployers, in a directory where deployers cannot replace the inode. The agent locks it once for at most 120s of contention, **including all rollback work**. Never wrap the hook with another flock acquisition. Legacy standalone `deploy/release.sh` still takes this lock and rejects duplicate SHAs. Provision `/var/lib/mailhub-api-deploy` root:root `0700` for durable state. Restrict the CodeDeploy agent revision tree to administrators.
- Install the reviewed `backend` upstream include in the effective TLS API location, under `/etc/nginx/mailhub-backend-upstream.conf`, root:root `0644`, not a symlink. Verify `nginx -T` with production overrides retained. The include may have blank lines, comments and exactly one active `server 127.0.0.1:8080 max_fails=3 fail_timeout=30s;` line (or 8081). The hook edits just its port and tests Nginx before every reload. Verify active routing with the helper below, not with the on-disk include alone.
- Install `/etc/mailhub/api-codedeploy.json` and the executable probe below, root-owned, without writable/symlink ancestors. Example config, **replace all three values** with those observed:

  ```json
  {"serviceUser":"ubuntu","nodeBin":"/home/ubuntu/.nvm/versions/node/v24.14.1/bin","pm2Home":"/home/ubuntu/.pm2"}
  ```

  The root launcher uses a fixed administrative PATH; npm, PM2 and the helper run via `runuser` with the account's home and a clean environment. Never configure UID 0. Ensure host recovery/run-on-boot can restore the committed **API only** using its recorded release/port, without resurrecting stale API entries from a global PM2 dump. Rehearse reboot and verify the worker's independently managed startup; the deployment deliberately does not rewrite worker persistence.

## Managed readiness helper (activation gate)

Provision `/usr/local/libexec/mailhub-api-readiness` independently of the revision. No fixed generic credential or fabricated check is shipped. Run it *as the configured service user*. It must finish within 60s, return **0 and exactly one stdout line** `READY <mode> <port>\n` only on full success; any uncertainty, timeout, credential error, unexpected status/body, or wrong upstream must exit nonzero. Suppress response bodies, usernames, cookies, bearer tokens, command traces and credentials in logs. The hook discards helper output except for the exact success comparison. An absent/unsafe helper or failed baseline blocks activation before release prep or traffic changes.

| Input example | Required transport and evidence |
| --- | --- |
| `mailhub-api-readiness direct 8081` | Send authenticated requests only to loopback `127.0.0.1:8081`, retaining the reviewed application Host/Origin and a stable fingerprint. Never silently follow redirects to production. |
| `mailhub-api-readiness ingress 8081` | Connect to **this instance's Nginx**, preserving the real TLS SNI, certificate verification and production Host/Origin (e.g. a local DNS override). Exercise the actual `/api` location. Independently prove **this probe's request** reached `127.0.0.1:8081`, e.g. correlate a random request ID with trusted local Nginx `$upstream_addr` access-log evidence. Reject a different/multiple/unknown backend. Do not infer routing from nginx.conf, DNS, `200`, the expected argument, or cache. |

Reviewed implementation outline: obtain an independent pre-provisioned managed test-account session via the site's vault/OTP mechanism; send authenticated `GET /api/users/me` (200, expected wrapped managed identity; exercises the DB), `POST /api/auth/refresh` (201, expected wrapped fresh access token **and** replacement refresh cookie; exercises Redis session read/rotation), then `/api/users/me` with the new token (same managed identity). Maintain stable IP/user-agent fingerprints and verified cookie handling within each transport. Use dedicated/direct and ingress sessions if fingerprints differ, bounded retries for graceful Nginx worker turnover, uncached requests, and atomic secret-store cookie rotation. Test deliberate DB unavailability, missing Redis session, stale credential, expired token, wrong upstream, wrong identity and TLS failure on a disposable host. A TCP connect, 401, generic HTML/JSON 200, or standalone DB/Redis ping is **not** readiness. Do not print a successful attestation from an unconditional stub.

## Switch and rollback

`ValidateService` runs the entire transaction directly from the CodeDeploy revision, not a mutable `current` path. It verifies the archive and original live PM2/socket identity, establishes both direct and ingress baseline, and stages a clean `npm ci --omit=dev --engine-strict --ignore-scripts` as the service user before linking `.env`. An existing SHA is compared against the complete clean tree (all installed files, byte contents, permissions, link targets and extra/missing entries); differences fail without overwriting the release. A verified already-serving SHA is a no-op.

The candidate runs only `pm2 start <release>/deploy/ecosystem.config.cjs --only mailhub-server-<inactive-port>`. Unrecorded occupied slots (including stopped PM2 name collisions) fail closed. The initially serving API may be `mailhub-server` or the port-specific name. A previous API stays alive; a later deployment can reuse it for rollback, or retire only its exact recorded inactive PID/name/CWD/script/start time after at least 120s and no established connections. Do not share these ports with other services.

Before any candidate start/switch a root-only, fsynced journal records the exact previous upstream bytes. After direct candidate validation, Nginx is tested/reloaded and authenticated ingress must attest the new port. **Even on the first deployment** a failure restores the previous include, tests/reloads it if necessary, proves the old route, and only then cleans the failed candidate. The original serving process is never stopped for this rollback. Failed recovery leaves the journal and both possible targets available, returns failure and requires investigation; a subsequent invocation recovers the journal under lock before beginning a new switch. Hard kill is not synchronous rollback: rerun a trusted revision promptly and alert on a retained `pending` journal. Redo a previous successful revision to roll back normally. No DB rollback belongs here.

For manual rescue freeze automation, hold the same shared flock, inspect the journal, both listeners/PM2 identities and effective Nginx configuration. Restore recorded `pending.old` (or the last successful `previousUpstream`) **only after** positively identifying its healthy previous API. Atomically restore the include, test, reload, and attest the restored ingress. Leave unknown processes and the journal alone until the incident owner has reconciled them. Do not invoke the locking hook inside this shell. Record SHA, port, PID/CWD, timestamps and redacted attestation outcomes, not secrets.

Local mocked verification: `bash test/deploy-release.sh && bash test/api-codedeploy.sh` using `.nvmrc`. These tests do not contact EC2, databases, mail, Redis, or AWS and do not certify the host's probe or configuration.
